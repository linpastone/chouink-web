論文審查

SELECT DISTINCT author_id AS id
FROM comments
WHERE author_id = viewer_id
ORDER BY id ASC;

語句拆解

  1. SELECT DISTINCT author_id AS id

    • SELECT：選取資料。

    • DISTINCT：關鍵詞，用來「去除重複」的結果。如果某個作者自己留言了好幾次，系統只會顯示該作者的 ID 一次。

    • AS id：將 author_id 這個欄位名稱改顯示為 id。

  2. FROM comments

    • 指定資料來源是名為 comments（留言）的資料表。

  3. WHERE author_id = viewer_id

    • 這是篩選條件，找出 author_id（留言作者）與 viewer_id（瀏覽留言的人/該文原作者）完全相同的資料行。這在社交平台中通常代表「留言者與該文作者是同一人」。

  4. ORDER BY id ASC

    • ORDER BY：排序。

    • id：依據剛才選出的 ID 進行排列。

    • ASC：由小到大（遞增）排序。遞減排序 (DESC)隨機排序 (RAND)

題目 #3 – 熱門實驗室

SELECT l.name AS popular_lab
FROM students s
JOIN labs l ON s.lab_id = l.lab_id
WHERE s.id LIKE '2021%'
GROUP BY l.lab_id, l.name
HAVING COUNT(s.id) >= 3;

1. 指令邏輯分析

  • SELECT l.name AS popular_lab：選取實驗室名稱，並將欄位顯示名稱設為 popular_lab。

  • FROM students s JOIN labs l ON s.lab_id = l.lab_id：將 students 表 (簡稱 s) 與 labs 表 (簡稱 l) 透過共有的 lab_id 欄位串連起來。

  • WHERE s.id LIKE '2021%'：這是篩選條件，只抓取學號開頭為 2021 的學生（代表 2021 年入學的學生）。

  • GROUP BY l.lab_id, l.name：將篩選出來的資料按照「實驗室」進行分組，以便統計每個實驗室有多少名學生。

  • HAVING COUNT(s.id) >= 3：這是「分組後的篩選條件」。它會過濾掉分組後人數小於 3 人的實驗室，只留下人數達到 3 人（含）以上的「熱門實驗室」。

2. 執行結果解讀

  • 查詢顯示結果為 "Cyber Security"。

  • 代表在資料庫中，屬於 2021 年入學的學生裡，只有「Cyber Security」這個實驗室的人數達到了 3 人或以上。

關鍵知識點：為什麼要用 HAVING 而不是 WHERE？

這是一個非常經典的 SQL 面試考題：

  • WHERE：是在資料分組之前進行篩選（用來篩選單一紀錄，如：篩選特定入學年）。

  • HAVING：是在資料分組之後進行篩選（用來篩選聚合後的結果，如：篩選統計人數總和）。

題目 #4 – 櫥窗購物



SELECT l.shopper_id, COUNT(l.entered_id) AS count_no_buy
FROM logs l
LEFT JOIN orders o ON l.entered_id = o.entered_id
WHERE o.order_id IS NULL
GROUP BY l.shopper_id;


1. 指令邏輯分析


    

  • 

    LEFT JOIN orders o ON l.entered_id = o.entered_id：這一步是關鍵。它將「所有訪問紀錄 (logs)」與「訂單紀錄 (orders)」進行連接。LEFT JOIN 會保留 logs 中的所有資料，即使在 orders 表中找不到對應的 entered_id。
    

    • 

  • 

    WHERE o.order_id IS NULL：這是一個過濾技巧。當 LEFT JOIN 後，如果 o.order_id 為 NULL，表示該訪問紀錄在訂單表中找不到對應的訂單，意味著該次訪問沒有產生購買行為。
    

    • 

  • 

    GROUP BY l.shopper_id：將篩選出來的「未消費」紀錄按照每個 shopper_id (顧客 ID) 進行分組。
    

    • 

  • 

    COUNT(l.entered_id) AS count_no_buy：統計每個顧客在 logs 中總共有幾次「未產生訂單的造訪紀錄」，並將結果命名為 count_no_buy。
    

    • 



2. 執行結果解讀


    

  • 

    13 號顧客：有 1 次造訪但沒有購買。
    

    • 

  • 

    39 號顧客：有 2 次造訪但沒有購買。
    

    • 

  • 

    52 號顧客：有 2 次造訪但沒有購買。
    

    • 



關鍵知識點：為什麼要用 LEFT JOIN + WHERE IS NULL？


這是 SQL 中篩選「不存在關係」的標準寫法：


    

  • 

    如果直接用 INNER JOIN，系統只會顯示「有產生訂單」的顧客，因為 INNER JOIN 會剔除所有沒有對應資料的行。
    

    • 

  • 

    透過 LEFT JOIN 並檢查右側資料表是否為 NULL，就能精準地把「有訪問紀錄但沒有訂單紀錄」的數據抓出來。
    

    • 





題目 #5 – 退選的組員


SELECT student_id
FROM takes
WHERE parner_id NOT IN (
    SELECT student_id FROM takes
);


1. 指令邏輯分析


    

  • 

    外層查詢 (Outer Query)：SELECT student_id FROM takes
    

      

    • 

      從 takes 資料表中選出所有的學生 ID。
      

      • 

    

    • 

  • 

    子查詢 (Subquery)：SELECT student_id FROM takes
    

      

    • 

      這是一個獨立運作的查詢，它先產生了一份所有學生 ID 的完整名單。
      

      • 

    

    • 

  • 

    WHERE parner_id NOT IN (...)：
    

      

    • 

      這是核心邏輯。系統會檢查每一行的 parner_id（合作夥伴 ID）。
      

      • 

    • 

      如果這個 parner_id 不在剛剛子查詢產生的那個 ID 名單中，條件就會成立（True）。
      

      • 

    • 

      這通常用來篩選出無效的合作夥伴連結或處理異常數據。
      

      • 

    

    • 



2. 執行結果解讀


    

  • 

    結果顯示為 3 和 6。
    

    • 

  • 

    這代表在 takes 資料表中，學生 3 號和 6 號的 parner_id 所指向的那個 ID，並沒有出現在「所有學生 ID」的清單內。
    

    • 

  • 

    資料意義：這在資料庫維護中很常見，是用來檢查「資料一致性」的。比如，如果 parner_id 應該要對應到合法的學生 ID，那麼 3 號和 6 號的數據可能就代表了「合作夥伴已離校」或「合作夥伴 ID 輸入錯誤」。
    

    • 



學習建議：關於 NOT IN 的小細節


使用 NOT IN 時要特別注意 NULL 值 的陷阱：


    

  • 

    如果子查詢結果中包含 NULL 值，NOT IN 運算子可能會導致外層查詢返回空結果（即使實際上有些資料符合條件）。
    

    • 

  • 

    在處理這類查詢時，如果遇到結果不如預期，可以嘗試加上 WHERE parner_id IS NOT NULL 來排除空值影響。
    

    • 





題目 #6 – 考試通過率


寫法A 顯示 4 位小數點，無考生時顯示 0.0000 / NULL


SELECT 
    t.test_id,
    ROUND(COUNT(CASE WHEN s.result = 1 THEN 1 END) / COUNT(s.examinee_id), 4) AS pass_rate
FROM tests t
LEFT JOIN signups s ON t.test_id = s.test_id
GROUP BY t.test_id;


這段 SQL 指令非常精彩，它展示了如何在資料庫查詢中進行條件式統計 (Conditional Aggregation) 與算術計算，用來計算每個測驗的「通過率」。


以下是詳細的拆解與執行邏輯：


1. 指令邏輯分析


    

  • 

    LEFT JOIN：將 tests 表與 signups 表連接，確保即使某個測驗完全沒有人報名，該測驗也會出現在結果中（如結果中的 test_id = 3）。
    

    • 

  • 

    CASE WHEN s.result = 1 THEN 1 END：這是一個非常有用的條件式邏輯。
    

      

    • 

      如果 result 為 1（假設代表通過），則回傳 1。
      

      • 

    • 

      如果不為 1，則回傳 NULL（因為沒有 ELSE 子句，預設為 NULL）。
      

      • 

    

    • 

  • 

    COUNT(...)：這也是一個小技巧。COUNT 函數會自動忽略 NULL 值。因此，COUNT(CASE ...) 的結果就是所有通過的人數。
    

    • 

  • 

    / COUNT(s.examinee_id)：除以總報名人數。
    

    • 

  • 

    ROUND(..., 4)：將最終算出的比例四捨五入到小數點後 4 位。
    

    • 



2. 執行結果解讀


    

  • 

    test_id = 1：通過率為 0.5000（50%）。
    

    • 

  • 

    test_id = 2：通過率為 0.3333（約 33%）。
    

    • 

  • 

    test_id = 3：顯示為 NULL。
    

      

    • 

      為什麼會出現 NULL？ 因為該測驗沒有人報名，COUNT 的結果為 0。在 SQL 中，「任何數除以 0」會產生 NULL（或錯誤）。這正是為什麼您會看到 1 warning，這在資料分析中是預期之內的現象。
      

      • 

    

    • 



寫法B 使用 AVG 函數自動計算布林值平均，無考生時為 NULL


SELECT 
    t.test_id,
    ROUND(COUNT(CASE WHEN s.result = 1 THEN 1 END) / COUNT(s.examinee_id), 4) AS pass_rate
FROM tests t
LEFT JOIN signups s ON t.test_id = s.test_id
GROUP BY t.test_id;


1. 條件式統計 (CASE WHEN + COUNT)


SQL 中的 COUNT() 函數，其邏輯是：「只會計算非 NULL 的值」。


    

  • 

    您寫的 CASE WHEN s.result = 1 THEN 1 END：
    

      

    • 

      當符合條件（通過）時，它會輸出 1。
      

      • 

    • 

      當不符合條件（失敗）時，系統預設不寫任何 ELSE，所以它會輸出 NULL。
      

      • 

    

    • 

  • 

    當 COUNT() 包住這個 CASE 時，它實際上只會統計那些「成功的次數」（因為 NULL 被自動忽略了）。
    

    • 



2. 分母與結果的處理


    

  • 

    COUNT(s.examinee_id)：這是統計該測驗「所有報名的人數」（分母）。
    

    • 

  • 

    相除：成功的次數 / 總報名人數 = 通過率。
    

    • 



3. 為甚麼會出現 NULL？（除以零問題）


當 test_id = 3 時，因為沒人報名：


    

  • 

    分母 (COUNT) 的結果是 0。
    

    • 

  • 

    在數學與資料庫運算中，任何數除以零都是「未定義」的，所以在 MariaDB 中會直接回傳 NULL。
    

    • 



總結


這段語法是用來進行「分組統計」的高級技巧：


    

  • 

    不使用多個複雜的子查詢 (Subqueries)。
    

    • 

  • 

    只用一次掃描 (Single Pass) 就把每個 test_id 的分子（通過數）和分母（總數）算出來。
    

    • 



















🌟 絕對重點：交易管理 (Transactions) 與 ACID 屬性




在交易處理中，必須確保以下 ACID 屬性，這部分是考試的關鍵：




    

  • 原子性 (Atomicity)：不可分割，交易中的操作必須「一起成功或一起失敗」。
    • 
    

  • 一致性 (Consistency)：確保每次交易後的資料一致性，這是交易設計器 (Transaction designer) 的責任，設計者不需擔心併發和系統故障的問題。
    • 
    

  • 隔離性 (Isolation)：可以變形（先後順序改變）但不能同時執行。這意味著執行過程不一定是嚴格串行的，而是可序列化的 (Serializable)。
    • 
    

  • 持久性 (Durability)：確保交易完成後資料永久保存。
    • 
    

  • 備註：TP monitor 主要負責確保原子性、持久性與特定級別的隔離性，提供無故障且非併發的抽象環境。

    

    • 





🌟 絕對重點：外來鍵與完整性限制 (Integrity Constraints)




    

  • 處理外鍵違規 (Handling Foreign Key Violations)：您的筆記明確指出這是「考試必考 1-50」。
    • 
    

  • 外來鍵 (Foreign Key) 定義：若關聯 R1 中的屬性 A1 參照 R2 中的屬性 A2，則只要 A1 有值，R2 中就必須有對應的元組其 A2 值相同，且 A2 必須是 R2 的候選鍵 (Candidate key)。
    • 
    

  • 參照完整性 (Referential integrity)：上述 A2 必須是候選鍵的規定即為參照完整性；若 R2 中不存在對應的列，即屬違反參照完整性。
    • 
    

  • 完整性限制 (Integrity constraints)：您的筆記特別標註「簡報要有」。
    • 





💡 重點一：實體關聯圖 (ER Diagram) 與資料屬性




    

  • 實體 (Entity)：指我們希望儲存資訊的人、地點、事件或事物。
    • 
    

  • 關聯 (Relationship)：實體之間的連結，關係本身也可以被視為一種特殊的實體。
    • 
    

  • 屬性 (Properties)：實體的特徵，可以是簡單或複雜的。
    • 
    

  • 計算屬性設計：有些資料（例如 GPA）不需要實際儲存，而是在需要時計算出來即可。
    • 
    

  • ER圖拆分設計：例如「訂單」，在設計上可以被拆成「訂單主檔案」以及「訂單明細」
    • 





💡重點二：關聯式資料模型 (Relational Data Model) 基礎




    

  • 發展背景：由 Codd 在 1970 年代提出，是資料庫歷史上最重要的創新，基於邏輯與數學。
    • 
    

  • 結構對應：數學上的「關係 (Relation)」對應到資料庫的資料表 (Table)；「元組 (Tuple)」對應到列 (Row)；「屬性 (Attribute)」對應到欄 (Column)
    • 
    

  • Tuple 特性：元組的排序是無關緊要的 (Tuple ordering immaterial)，順序改變不影響資料表意義。
    • 
    

  • 操作 (Operations)：運算子可以從現有的資料表衍生出新的資料表，分為一元（如刪除特定列）與二元（如聯集、笛卡兒積）運算，這些數學特性能用來判斷等價性，對查詢最佳化 (Query Optimization) 非常重要。
    • 





💡 重點三：資料庫系統架構 (三層抽象結構)




資料實際是以位元(bits)儲存，但為了方便使用，資料庫將其分為三個抽象層級，各自擁有獨立的 Schema（結構描述）：






    

  1. 外部層 (External Level)：支援單一或多群使用者，不同使用者需要不同的視觀表 (Views)，通常透過 SQL Views 實作。
    2. 
    

  2. 概念層 (Conceptual Level)：全域的邏輯表示法，由所有使用者共用，代表資料的底層意義，是資料庫設計的基礎，透過概念 DDL (Conceptual DDL) 實作。
    3. 
    

  3. 內部層 (Internal Level)：實體層 (Physical layer)，包含區塊 (Blocks)、分頁 (pages)、I/O，與硬體相關，包含 Hash、Heap、B-tree 等資料結構及指標 (pointers)。
    4. 
    

  4. 資料獨立性 (Data Independence)：資料庫分離了邏輯與實體資料表示法，讓應用程式可以修改，而不需要改變底層資料結構。
    5. 





💡 重點四：資料庫應用與系統組成




    

  • 系統組成：資料庫系統由 Data、Hardware、Software、Users 組成。
    • 
    

  • 資料庫使用情境：

      

    • OLTP (線上交易處理)：例如紀錄日常行為，「買了3罐湯和1盒餅乾，更新資料庫以反映此事件」。
      • 
      

    • OLAP (線上分析處理)：大範圍查詢，例如「去年冬天在東北地區所有門市，有多少顧客同時買了湯和餅乾？」。
      • 
      

    • Data Mining (資料探勘)：尋找潛在模式，例如「顧客常一起購買的食物有沒有什麼有趣的組合？」。
      • 

    

    • 





💡 重點五：SQL 標準與權限控制




    

  • 標準演進：SQL-92 是現代 SQL 的基礎，隨後的 SQL:1999 增加了遞迴查詢、物件導向等特性，SQL:2003 增加了 XML 與 Window functions 相關特性。
    • 
    

  • 權限控制 (GRANT)：可授權的操作包含 SELECT, INSERT, DELETE, UPDATE, REFERENCES。例如可以特別指定僅對特定欄位（如 Grade）授予 UPDATE 權限，但在標準 SQL 中不能對單一欄位限制 SELECT，不過可以透過其他方式模擬。
    •
